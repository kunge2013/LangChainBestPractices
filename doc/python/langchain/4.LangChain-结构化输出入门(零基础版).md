# LangChain 结构化输出入门（零基础版）

> 这篇是写给"完全没接触过"的人的。不用懂编程、不用懂 LangChain，只用生活里的例子，
> 把整件事讲明白。
>
> 想深入一点的：`2.LangChain-结构化输出(JSON保证与可靠性).md`（有哪些策略、怎么搭可靠闭环）、
> `3.LangChain-结构化输出原理(JSON保证与可靠性).md`（底层原理）。
> 这篇只讲三件事：**整体流程、tools、tool_choice**。

## 1. 先讲个故事：去诊所看病，要填一张病历表

想象你生病了，去诊所。整个过程是这样的：

1. **你说话**：告诉前台"我头疼、发烧，两天了"。
2. **前台有一张"病历表"**：上面印好了格子——
   姓名：____
   年龄：____
   症状：____
   风险等级：低 / 中 / 高
3. **前台按规矩填表**：把你的话填进对应的格子里，不闲聊、不写别的。
4. **填好的表交给你**：一张整整齐齐的病历表。
5. **你检查一下**：姓名填了吗？年龄是不是数字？有没有填错栏？不对就让她重填。
6. **存进电脑**：这张表以后就能被电脑自动处理。

**"结构化输出"就是这件事**——让大模型(前台)把你说的话，填进一张"规定好的表"里交回来。

不用大模型的时候，它像一位"随口聊天的朋友"，你问什么它自由回答，说多少、怎么说都行。
用了"结构化输出"，它像那位"必须按表格填的前台"，**说的话被硬塞进固定格式**，方便电脑读取。

## 2. 整条流水线，一张图看懂

```mermaid
flowchart LR
    A["你：一句话<br/>（输入）"] --> B["打包成一个大包裹<br/>（请求体）"]
    B --> C["大模型<br/>（前台小姐姐）"]
    C --> D["填好的表<br/>（JSON，输出）"]
    D --> E["检查表对不对<br/>（校验）"]
    E --> F["存进电脑<br/>（Python 数据）"]
```

从左往右读，就六个环节。下面一步一步拆开讲。

## 3. 环节一：你说一句话（输入）

```
患者张三，32岁，因发热咳嗽就诊，症状持续三天，评估为高风险，联系电话13800000000。
```

大白话翻译：**这就是你打给大模型的那句话**。里面有人名、年龄、症状、风险等级、电话——
但都是"藏在话里的"，像一锅粥，电脑没法直接用。

## 4. 环节二：打包成"大包裹"（请求体）—— 这里有两个主角：tools 和 tool_choice

普通聊天时，发给大模型的包裹里**只有你的一句话**。
结构化输出时，包裹里**多出两块东西**，和你说的话并排放在一起：

```
┌─────────────────────────────────────────────┐
│ 这个大包裹里，有三块是并排的：                   │
│                                             │
│  ① 你说的话        messages                 │
│  ② 空表清单        tools                    │  ← 把要用的"表格"装进去
│  ③ 命令            tool_choice              │  ← 命令大模型：必须用这张表！
└─────────────────────────────────────────────┘
```

### 4.1 tools = 空表清单（"工具"或"表单"）

`tools` 里装的是**你要大模型照着填的"空表"**。大白话：这是你递给前台的那张病历表。

这张表长这样（只看懂大概意思就行）：

```json
{
  "type": "function",
  "function": {
    "name": "PatientRecord",              // 表的名字：病历表
    "description": "自由文本 -> 结构化病历抽取", // 说明这表干嘛用的
    "parameters": {                        // 表上印了哪些格子
      "type": "object",                    // 这张表是一张"物件表"
      "required": ["name", "age", "symptoms", "risk_level"],  // 必须填的格子
      "properties": {                      // 每个格子长什么样
        "name":       {"type": "string"},              // 姓名：要填文字
        "age":        {"type": "integer"},             // 年龄：要填数字
        "symptoms":   {"type": "array", "items": {"type": "string"}},  // 症状：填一串文字
        "risk_level": {"type": "string", "enum": ["low", "medium", "high"]}, // 风险：只能三选一
        "contact":    {"type": ["object", "null"]}     // 联系方式：可填可不填
      }
    }
  }
}
```

> 注意看："风险等级"那格写着 `enum: low / medium / high`，意思就是**只能从这三个里面挑一个**，
> 不能自己发明一个"SEVERE"。这就是表格在管着大模型，不许乱填。

**一句话记住 `tools`：它就是"菜单/空表清单"，告诉大模型"有这些表可以用"。**

### 4.2 tool_choice = 命令（必须用哪张表）

光给大模型一张表还不够——大模型可能偷懒，不回填好的表，而是像聊天一样随便说两句。
所以还要下一条**命令**：你必须用这张表！

```json
{
  "type": "function",
  "function": {"name": "PatientRecord"}
}
```

大白话翻译：**"就用这张叫 PatientRecord 的表，别的不许用，也别闲聊，填表！"**

**一句话记住 `tool_choice`：它是"死命令"，把大模型锁死在填表这件事上。**

> 打个比方：`tools` 是"菜单上有很多菜"，`tool_choice` 是"服务员，我就要这道菜，别的不要"。

## 5. 环节三：大模型 = 一个特别认真的前台

大模型收到这个大包裹后，干三件事：

1. **读包裹**：看到"你说的话"——知道了你的病情。
2. **看空表清单**：看到那张 `PatientRecord` 表——知道了要填哪些格子、每个格子什么格式。
3. **执行命令**：被 `tool_choice` 命令了，必须填表，不许自由发挥。

于是它把你说的话里的信息，**一条条装进对应的格子里**。

> 这里有个关键的小秘密：那张表（tools）不是塞在你说的"话"里的，而是和你说的话**并排**放在
> 包裹里的。所以哪怕"你说的话"一个字没改，大模型也**确实读到了这张表**——
> 就像前台看得到那张空表，但表不是你说的话的一部分。

## 6. 环节四：填好的表交回来（输出 JSON）

大模型把填好的表，用一种叫 **JSON** 的格式交回来：

```json
{
  "name": "张三",
  "age": 32,
  "symptoms": ["发热", "咳嗽"],
  "risk_level": "high",
  "contact": {"phone": "13800000000"}
}
```

JSON 就是**一种让电脑能读懂的"填表格式"**：`"名字"：内容`，一条一条列清楚。
对照着空表看，每一项都填对了：姓名是文字、年龄是数字、风险等级是三个选项之一。

## 7. 环节五：检查表对不对（校验）—— 大模型也会填错

大模型不是机器，**有时候会填错**。所以交回来之后，我们要检查：

| 检查什么              | 例子                                             |
| ------------------- | ---------------------------------------------- |
| 有没有漏填？            | 姓名那格空的？                                       |
| 类型对不对？            | 年龄写成 "32"（文字）而不是 32（数字）？                      |
| 是不是在选项里？          | 风险等级填了 "SEVERE"，可表上只有 low / medium / high？      |
| 有没有多填表格上没有的栏？    | 表格上没有"心情"，它却填了个"心情"？                          |

**任何一个检查不过，就进入"退回去重填"环节。**

### 重填（重试）：把错误告诉大模型，让它自己改

就像前台填错，你把表退回去，**在旁边写一句"这一栏填错了：年龄应该是数字"**，让她改。

```text
【上一次输出未通过校验，请仅修复以下错误并重新输出 JSON】
root.age: 类型应为 integer，实际 str
```

大模型看到这句批注，**针对性改正**，再把表交回来。最多给它几次机会（本文默认 2 次重试）。

### 还是填不好？（兜底）

给了几次机会还填不对，就返回一个**备用答案**（默认是没有/空），并且记一笔"这次失败了"。
**宁可返回空，也不把一个填错的表拿去用**——这就是"可靠性"。

## 8. 环节六：存进电脑（Python 数据）

填好的 JSON 经过校验没问题后，就变成 Python 能直接用的数据对象了。
以后你想查"这个病人风险等级是多少"，直接读这个对象就行，**不用再去听大模型唠唠叨叨**。

## 9. 把六个环节连起来，再看一遍

用真实的例子走一遍：

| 环节            | 内容                                                                                                  |
| ------------- | --------------------------------------------------------------------------------------------------- |
| ① 输入          | "患者张三，32岁，因发热咳嗽就诊……"                                                                          |
| ② 打包          | messages(你的话) + tools(PatientRecord 空表) + tool_choice(必须用这张表)                                  |
| ③ 大模型处理      | 读你的话 → 看表 → 命令强制填表                                                                            |
| ④ 输出          | `{"name":"张三","age":32,"symptoms":["发热","咳嗽"],"risk_level":"high",...}`（JSON）                    |
| ⑤ 校验 + 重试     | 检查必填/类型/选项/多余栏；不对就带上错误批注重试                                                               |
| ⑥ 存进电脑       | 通过校验的 JSON → Python 数据对象，可直接使用                                                               |

真实跑一次（GLM-5.2），三个例子看结果：

| 例子        | 大模型表现                                          | 最后结果                           |
| --------- | ---------------------------------------------- | ------------------------------ |
| 完整病历    | 一次就填对                                         | 成功，拿到整整齐齐的病历表               |
| 信息太少    | 第一次没填表、净聊天 → 被拦下重试 → 第二次填对              | 成功（用了 2 次）                   |
| 无关内容    | "今天天气不错"——它三次都不肯硬编病历 → 重试耗尽            | 返回空（兜底），不硬凑                 |

## 10. 一页纸总结（背下来这几点就够了）

| 名词          | 大白话意思                                  | 负责什么           |
| ----------- | ------------------------------------- | -------------- |
| 输入（messages） | 你说的话                                | 提供信息           |
| tools       | 空表清单（菜单）                            | 告诉大模型"要填这张表" |
| tool_choice | 命令（服务员，就要这道菜）                      | 锁死大模型必须填表     |
| 输出（JSON）    | 大模型填好的表，电脑能直接读的格式                 | 交付结果           |
| 校验 + 重试     | 检查 + 退回去让大模型改                        | 保证质量           |
| 兜底          | 改不好就返回备用答案，不拿错的硬用                 | 保证可靠           |

**三句话彻底记住**：

1. **`tools` 是空表清单**——你要大模型照着填的"表"装在这里。
2. **`tool_choice` 是死命令**——命令大模型必须用这张表，不许闲聊。
3. **大模型也会填错**——所以"校验 + 重试 + 兜底"才是真正的保障，光靠表格本身不够。
