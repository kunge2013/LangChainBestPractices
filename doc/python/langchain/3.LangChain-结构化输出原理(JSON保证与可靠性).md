## 0. 本文定位：与 §2 的分工

`2.LangChain-结构化输出(JSON保证与可靠性).md` 回答「**有哪些策略、怎么搭可靠闭环**」——策略全景、
最小可靠闭环、观测、企业级落地。本文回答「**底层原理：发给模型的到底是什么、模型为什么返回 JSON、
每一层保证是靠什么机制生效的**」。

一句话主线：

> **结构化输出的一切，都发生在 HTTP 请求体顶层的平级字段里；模型返回 JSON 是「工具调用协议输出格式」
> 的必然结果，而不是提示词或 Python 继承带来的魔法。**「提示词零改动」不等于「模型没看到 schema」——
> 框架经 `tools` 通道把 schema 平行送给了模型。

## 1. 一条主线：请求体就是契约

先看纯 Python 版 `pure_structured_output.py` 里 `build_function_calling_payload` /
`build_json_mode_payload`——它们手拼的就是**发给模型的完整请求体**。结构化输出与普通聊天的差别，
只在顶层多出的几个**与 `messages` 平级**的字段：

```python
def build_function_calling_payload(text: str) -> dict:
    """§2.6 主通道：schema 装进 tools[].function.parameters，提示词零改动。"""
    p = _base_payload(text)
    p["tools"] = [{"type": "function", "function": {
        "name": SCHEMA["name"], "description": SCHEMA["description"], "parameters": SCHEMA}}]
    p["tool_choice"] = {"type": "function", "function": {"name": SCHEMA["name"]}}
    return p


def build_json_mode_payload(text: str) -> dict:
    """对照通道：不发 tools，schema 必须写进 prompt（且含 "JSON" 字样）。"""
    p = _base_payload(text)
    p["messages"] = [
        {"role": "system", "content": "你只输出合法 JSON，且必须符合以下 JSON Schema：\n"
                                      + json.dumps(SCHEMA, ensure_ascii=False)},
        {"role": "user", "content": text},
    ]
    p["response_format"] = {"type": "json_object"}
    return p
```

`_base_payload` 只装「模型 + 消息 + 温度 + max_tokens」，与普通聊天完全一样：

```python
def _base_payload(text: str) -> dict:
    p = {"model": MODEL, "messages": [{"role": "user", "content": text}], "temperature": TEMPERATURE}
    if MAX_TOKENS:
        p["max_tokens"] = MAX_TOKENS
    if QWEN_THINKING_OFF:
        p["enable_thinking"] = False
    return p
```

于是真实跑通 GLM-5.2 的那一包请求体，顶层是这样的**平级三块**：

```json
{
  "model": "glm-5.2",
  "messages": [{"role": "user", "content": "患者张三，32岁，因发热咳嗽就诊……"}],
  "temperature": 0.7,
  "max_tokens": 20000,
  "tools": [
    {
      "type": "function",
      "function": {
        "name": "PatientRecord",
        "description": "自由文本 -> 结构化病历抽取的演示 Schema。",
        "parameters": {
          "type": "object",
          "additionalProperties": false,
          "required": ["name", "age", "symptoms", "risk_level"],
          "properties": {
            "name": {"type": "string"},
            "age": {"type": "integer"},
            "symptoms": {"type": "array", "items": {"type": "string"}},
            "risk_level": {"type": "string", "enum": ["low", "medium", "high"]},
            "contact": {"type": ["object", "null"], "additionalProperties": false,
                        "properties": {"email": {"type": ["string", "null"]},
                                       "phone": {"type": ["string", "null"]}}}
          }
        }
      }
    }
  ],
  "tool_choice": {"type": "function", "function": {"name": "PatientRecord"}}
}
```

**看清这张图，本主题就通了**：`messages` 是你写的聊天文本（提示词）；`tools` + `tool_choice`
是**独立于提示词的、携带 schema 的结构化参数通道**。后面四个小节逐一解释这张图上每个字段为什么存在、
模型又怎么因为它们而「返回 JSON」。

## 2. 机制一：模型为什么「知道」字段？（tools 通道注入）

最常见的疑问是：**模型知道需要哪些字段，是提示词层面做了什么处理，还是继承了 BaseModel Schema？**
两个答案都不准确——**两者都不是直接原因**。完整链路：

```
Pydantic 类 PatientRecord
   │ ① 请求构建期（纯 Python 侧，无网络）调用 model_json_schema()
   ▼
JSON Schema dict（type / required / properties / enum / additionalProperties…）
   │ ② convert_to_openai_tool() 拆成 function.name / description / parameters
   ▼
tools[].function 参数 + tool_choice（强制该工具）
   │ ③ HTTP POST {base}/chat/completions
   ▼
推理服务把 tools 里每个函数转成「特殊工具令牌」，追加进模型的输入上下文
   ▼
模型「读到」了字段名、类型、required、enum —— 只是不在你写的聊天文本里
```

- 「**继承了 BaseModel**」只是**客户端侧的 Python 类型安全**：它让 `model_json_schema()` 能产出 schema、
  让 `model_validate()` 能校验结果。它**不会**让模型知道任何东西——模型只知道协议层送进去的 token。
  `BaseModel` 在链路两端各用一次：前头产出 schema 喂给 API，后头校验返回结果；中间只有纯 JSON 往返，
  没有 Python 对象。
- 「**提示词层面处理**」同样不是主因：`function_calling` 通道下，你写的 `messages` 文本**一个字都没变**。
  schema 是走 `tools` 通道**平行**送进去的，所以才有「提示词零改动」的说法。

**对照 `json_mode` 就立刻明白**：它不发 `tools`，模型输入上下文里**没有任何字段定义**，
所以必须由你在 `system` 消息里把 schema 文本**自己写进提示词**——上面 `build_json_mode_payload`
就是这么干的。这正是 §4 表格里唯一一行「prompt 需要动手」的通道。

## 3. 机制二：模型为什么「返回 JSON」？（工具调用协议）

即使模型「看到」了 schema，它凭什么输出合法 JSON？答案在**工具调用协议的输出格式**：

- `function_calling` 通道下，`tool_choice` 强制模型**必须发起一次对 `PatientRecord` 的工具调用**，
  不能自由发挥聊天文本。
- 工具调用协议的输出格式规定：`tool_calls[].function.arguments` **必须是一个符合该函数
  `parameters` schema 的 JSON 字符串**。
- 模型在训练（指令微调 + 工具调用数据）时**内化了这个契约**，于是：

```json
"tool_calls": [{
  "function": {
    "name": "PatientRecord",
    "arguments": "{\"name\":\"张三\",\"age\":32,\"symptoms\":[\"发热\",\"咳嗽\"],\"risk_level\":\"high\"}"
  }
}]
```

**「返回 JSON」是协议输出格式的必然结果**，不是模型即兴发挥。但这是**条件概率**：模型仍可能
填错枚举（`risk_level: "SEVERE"`）、漏必填字段（`name` 缺失）、把数字输出成字符串（`age: "32"`）。
所以协议只保证「**是** JSON、大体符合 schema」——**是否符合你的 schema，最终防线永远在你自己的
校验层（§7 ③）**。这正是「模型侧尽力而为、校验层是硬保证」这一分工的由来。

## 4. 机制三：三条通道的差异本质

三种 `method` 在同一条链路上的全部差异，只看**两件事**：schema 装进哪个 API 参数、prompt 是否被改动。

| method             | 源码位置（langchain-openai 1.4.1） | schema 装进哪个 API 参数                                      | prompt 文本      | JSON 返回载体            | 保证强度                  |
| ------------------ | ----------------------------- | --------------------------------------------------------- | ------------- | --------------------- | --------------------- |
| `function_calling` | `chat_models/base.py:2490`    | `tools[].function.parameters` + `tool_choice`               | **零改动**       | `tool_calls[0].args`  | 强（协议原生工具调用）          |
| `json_mode`        | `chat_models/base.py:2521`    | **无**（不发 schema）                                          | **需自己写 schema 进 prompt** | `content`             | 中（只保证合法 JSON）         |
| `json_schema`      | `chat_models/base.py:2537`    | `response_format={"type":"json_schema",...}`                | **零改动**       | `content`             | 最强（服务端严格校验），仅 OpenAI/Claude/Gemini |

**`json_mode` 是唯一需要你在提示词里动手的通道**：`with_structured_output` 根本不会把 schema
传给模型，源码注释原话 *"you must include instructions for formatting the output into the
desired schema into the model call"*。模型此时只被 API 要求「输出合法 JSON」，不知道
`PatientRecord` 长什么样——所以 `build_json_mode_payload` 必须手动把 `SCHEMA` 文本拼进
`system` 消息。

## 5. 机制四：Pydantic 类 → JSON Schema 逐行映射

以 `schemas.py` 的 `PatientRecord` 为例，逐行看每个 Python 元素变成了什么、哪些**不会**发给模型：

```python
class RiskLevel(str, Enum):          # 枚举
    LOW = "low"; MEDIUM = "medium"; HIGH = "high"

class ContactInfo(BaseModel):        # 嵌套模型
    model_config = ConfigDict(extra="forbid")
    email: str | None = None
    phone: str | None = None

class PatientRecord(BaseModel):
    """自由文本 -> 结构化病历抽取的演示 Schema。"""   # ← 类 docstring
    model_config = ConfigDict(extra="forbid")          # ← 禁多余字段
    name: str = Field(strict=True)                     # strict 只影响客户端校验
    age: int = Field(strict=True)
    symptoms: list[str]
    risk_level: RiskLevel                              # 枚举
    contact: ContactInfo | None = None                 # 嵌套 + 可空 + 默认值
```

| Pydantic 元素                              | JSON Schema 产物                                              | 是否发给模型 |
| --------------------------------------- | ---------------------------------------------------------- | ------ |
| `class PatientRecord`                    | `function.name = "PatientRecord"`（经 `convert_to_openai_tool` 提取） | ✓    |
| 类 docstring                             | `function.description`                                       | ✓    |
| `ConfigDict(extra="forbid")`             | `parameters.additionalProperties: false`（多输出字段即非法）        | ✓    |
| `name: str` / `age: int`                 | `properties.name.type = "string"` / `properties.age.type = "integer"` | ✓    |
| `symptoms: list[str]`                    | `properties.symptoms = {"type":"array","items":{"type":"string"}}` | ✓    |
| `risk_level: RiskLevel`                  | `properties.risk_level = {"type":"string","enum":["low","medium","high"]}` | ✓    |
| `contact: ContactInfo \| None = None`    | `properties.contact = {"anyOf":[{...object, "title":"ContactInfo"},{...null}],"default":null}` | ✓    |
| 必填字段 name/age/symptoms/risk_level     | `parameters.required`（可选字段 `contact` 不在其中）                | ✓    |
| `Field(strict=True)`                     | **无**——strict 是 pydantic-core 客户端校验指令，不进 JSON Schema     | ✗    |
| 类型注解里的 Python 细节 / 方法 / 注释     | **无**                                                         | ✗    |

两个容易误会的点：

1. **`strict=True` 不会发给模型**。它只影响客户端 `model_validate()` 是否做严格类型转换（§6），
   是「本地执法」，不参与「模型约束」。所以 schema 里 `age` 只有 `{"type":"integer"}`，没有 strict。
2. **嵌套模型自带 `title`**（`"title": "ContactInfo"`）是 `model_json_schema()` 的产物，会留在
   `anyOf` 里；顶层模型的 `title`/`description` 则被 `convert_to_openai_tool` 抽到
   `function.name`/`function.description`，使 `parameters` 保持纯 schema。

`pure_structured_output.py` 里的 `SCHEMA` 是**手写的等价简化**：为了让「一个 dict 走天下」更直观，
它把 `name`/`description` 也留在了 `parameters` 顶层（与 `function.name`/`function.description`
略冗余，删掉了 `title`/`default`）。真实 provider（含 GLM-5.2）对此宽容、照常可用，但要知道
`convert_to_openai_tool` 生成的「规范形」会去掉这份冗余。

## 6. 机制五：客户端如何还原（语法层 + Schema 层）

模型返回的 JSON 只是**字符串**，客户端要把它还原成数据对象。两层还原，任何一层失败都抛错，
交给修复层（§7 ④）重试。纯 Python 版与 Pydantic 版原理完全一致：

```python
# pure_structured_output.py：语法层 + 手写 Schema 层
def validate(raw: RawResult) -> dict:
    if not raw.json_str:
        raise ValueError(raw.note or "模型未返回可解析的 JSON")
    data = json.loads(raw.json_str)                     # ① 语法层
    errs = _check(data, SCHEMA)                         # ② Schema 层（手写递归）
    if errs:
        raise ValueError("；".join(errs))
    return data
```

```python
# simple_onefile.py：语法层 + Pydantic Schema 层
def validate(raw: RawResult, schema: type[BaseModel]) -> BaseModel:
    if not raw.json_str:
        raise ValueError(raw.note or "模型未返回可解析的 JSON")
    data = json.loads(raw.json_str)      # ① 语法层
    return schema.model_validate(data)   # ② Schema 层（Pydantic 严格校验）
```

- **语法层**：`json.loads` 只回答「是不是合法 JSON」。模型回纯文本、被 `max_tokens` 截断、
  带 ```json 围栏（`_strip_json` 兜底处理）——都在这一层暴露。
- **Schema 层**：`_check()` 递归等价于 `model_validate()` 在这套 schema 上做的全部检查：
  必填字段齐全、类型正确（`_match_type` 用 `type(value) is int` 排除 bool）、枚举合法、
  `additionalProperties:false` 禁多余字段、嵌套对象递归下钻。

两层合起来的语义是：**模型输出的 JSON 必须严格等于你的契约，差一点就判失败并进入重试**——
这就是「schema 级保证是硬保证」的落点。

## 7. 五层保证的实现原理

### ① 数据模型：schema 是「输入约束」也是「输出契约」

`PatientRecord`（或手写 `SCHEMA`）在链路两端各扮演一个角色：**发起时**被 `model_json_schema()`
转成喂给模型的约束（§5）；**收尾时**被 `model_validate()` 当裁判校验返回结果（§6）。
`extra="forbid"` 让契约变成「白名单」——模型多输出一个字段都算失败。

### ② 生成层：唯一的「外部世界」入口

闭环里只有它碰模型。它把「prompt → 模型输出」规范化为一个简单数据：

```python
@dataclass
class RawResult:
    json_str: str | None   # 可解析的 JSON 字符串；None 表示生成层没产出 JSON
    note: str = ""         # 失败原因（如 "content 中未找到 JSON 对象"）
```

对 `pipeline.py` 而言，`RealExtractor` 与 `FakeExtractor` 一视同仁，只认 `extract(text) -> RawResult`。
「规范化」的价值：**后面四层完全不必关心模型返回的是 tool_calls 还是 content**。

### ③ 校验层：语法层 + Schema 层（§6）

### ④ 修复层：把错误喂回 prompt = 模型自纠正

```python
FIX_TEMPLATE = "\n\n【上一次输出未通过校验，请仅修复以下错误并重新输出 JSON】\n{error}"
```

循环里 `attempt >= 2` 时 prompt 变成 `text + FIX_TEMPLATE.format(error=errors[-1])`：
模型看到的是**上一次具体的校验错误**（如 `root.age: 类型应为 integer，实际 str`），
于是针对性地修——这替代了 0.x 时代已移除的 `OutputFixingParser`，且次数、错误内容、日志、兜底全部由你掌控。

> **为什么重试真能救回失败？** 看一次真实观测（GLM-5.2，样本「信息缺失」）：
> attempt=1 模型回了纯文本澄清（**没走 tool call**，`content` 里也没 JSON）→ 语法层拦截
> `ValueError: content 中未找到 JSON 对象`；attempt=2 带上这条错误重发，模型这次乖乖输出合法 JSON
> （`{"name":"未知","age":0,...}`）。重试不是撞运气，而是**把失败原因变成了下一轮的有效输入**。

### ⑤ 兜底 + 观测：IO 与流程完全解耦

- **兜底层**：`max_retries + 1` 次全失败后返回 `fallback`（默认 `None`），并记一条 `fallback` 日志 + 失败计数。
- **观测解耦**（用户明确要求的设计）：流程里**只把日志攒成变量**（纯数据，不碰 IO），
  流程结束后才统一落盘：

```python
records: list[dict] = []          # 流程里只攒纯数据
...
records.append(_record(attempt, "retry", last_prompt, last_raw, None, errors[-1]))   # 不碰 IO
...
write_records(records)            # 流程结束，统一写 JSONL
```

`_record()` 是纯函数，返回一条可 JSON 序列化的 dict（`ts / request_id / status / attempt /
error / prompt / raw_json / parsed / latency_ms / provider / model / method`）；
`write_records()` 是唯一的 IO 落点。观测不干扰控制流：重试分支全程在内存里，
写盘只发生一次。生产版 `pipeline.py` 为崩溃可恢复性选择每 attempt 落盘，教学版刻意演示解耦。

## 8. 版本坑的原理：为什么默认 json_schema 会 400

`langchain-openai` **1.4+ 的 `with_structured_output` 不传 `method` 时，默认已是 `json_schema`**
（不再是 0.x / 早期 1.x 的 `function_calling`）。不传 method 时它发出
`response_format={"type":"json_schema",...}`，而：

- **`json_schema` 严格模式是较新的服务端能力，仅 OpenAI / Claude / Gemini 支持**；
- qwen / deepseek / glm 这些 OpenAI 兼容模型**只实现 function_calling + json_object**，
  收到 `response_format.type=json_schema` 直接 400：
  `The parameter response_format.type ... json_schema is not supported by this model`。

**修复：显式传 `method="function_calling"`（最稳）或 `"json_mode"`**。这不是「某个模型的小问题」，
而是「默认值随版本漂移 + 模型能力矩阵不同」叠加出的经典坑，所以本文所有代码一律显式传 method。

```json
 "latency_ms":31261,"provider":"openai-compatible","model":"glm-5.2","method":"function_calling"}
```

两个值得记录的观察：

1. **GLM-5.2 无需关 thinking**（不像 qwen，见 2.x §3.1）：`QWEN_THINKING_OFF` 只在
   dashscope/qwen 时置真，Volcengine + glm-5.2 直接带 `tool_choice` 也能跑，无 400。
2. **「信息缺失」首次回的是 content 纯文本而非 tool_calls**——生成层 `extract()` 先找
   `tool_calls[0].arguments`，找不到再退到 `content`，两个都拿不到 JSON 才算失败，
   校验层 + 修复层随即接管。这正好实证了 §3「模型侧尽力而为、校验层是硬保证」的分工。

## 10. 心法速记

- **请求体顶层字段就是契约**：`messages` 是提示词，`tools`/`tool_choice`/`response_format` 是平行的结构化通道。
- **JSON 来自协议通道，不是提示词**：「提示词零改动」≠「模型没看到 schema」。
- **模型返回 JSON 是条件概率**：协议保证「是 JSON」，不保证「符合你的 schema」。
- **校验是硬保证**：`json.loads`（语法层）+ `model_validate`/`_check`（Schema 层），两层都是你自己兜底。
- **重试 = 模型自纠正**：把上一次的校验错误喂回 prompt，重试才不是撞运气。
- **观测让失败可见**：records 攒变量、统一落盘，IO 与流程解耦；失败率 / 重试率是可告警的工程指标。
- **显式传 method**：默认值会随版本漂移（1.4+ 默认 json_schema），国产/开源模型认 function_calling。
